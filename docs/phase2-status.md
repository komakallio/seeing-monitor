# Seeing monitor: phase 2 status

Updated: October 2, 2026, at commit `05f04da`. Steps 0 to 12 are done, against the fakes and harnesses where hardware is involved. The items that wait for hardware or for you are in the blocker table. Every lane has reported. What remains waits for you or for hardware, and the blocker table lists it. The lead updates this file at every step boundary and whenever a lane lands a large piece, and the lanes do not edit it. The instructions are in `docs/phase2-kickoff.md`.

Main health: CI on `main` is green at `a022a5b`, and a nightly workflow (`nightly.yml`) runs the slow tests on three platforms and passed there. The runs of the later commits are queued: on October 2 the lanes pushed about one commit every two minutes, each run starts six jobs, and that outran the runners (the jobs of a run waited 20 minutes to start). `05f04da` makes one run go at a time on `main`, with at most one waiting behind it, so the newest commit is always the one that gets tested and the commits in between have no run of their own. CI went red twice after `880e21f`. The lock went stale at `88531ea` (a new `websockets` dependency), and the lead fixed it in `37262d5`. The JavaScript scenarios of the web lane failed under Node from `1fca0dc` to `f669a32` (no Node is installed on the dev machine, so only CI runs them), and the lane fixed them in `dc3c77e` and `e5a1075`. Before `880e21f`, `main` was red for eight runs, for three reasons: the lock went stale after a new dev dependency (`shellcheck-py`), the secret scan flagged two false positives, and six test strings in the web lane's host tests tripped the repository check. The lead fixed them in `baafe2f`, `a8c6ff1`, and `880e21f`, and `tools/scan_secrets.py` now puts the secret scan in the commit routine, so the lanes catch that kind before they push. The lock goes stale whenever a lane adds a dependency (`sep`, `psycopg`, `shellcheck-py`, `websockets`), and the lead regenerates it each time.
